## 1. Цель и вариант

Цель — диагностировать, почему данные «невидимы» для статического парсера, собрать их браузерной
автоматизацией и дешёвой альтернативой, сравнить подходы по измеренным метрикам и повторить сценарий в no-code.

| Параметр | Значение |
|---|---|
| Основной источник | `https://quotes.toscrape.com/login` + разделы за входом (`/page/N/`, `/tag/<тег>/page/N/`) |
| Проверяемый механизм | форма входа с CSRF-токеном, переиспользование `storage_state`, пагинация после авторизации |
| Контрольный статический источник | `https://quotes.toscrape.com/page/1` |
| Учётные данные | учебные, `student`/`student` (сайт принимает любые), в `.env`, в выводе маскируются |
| Единица набора | «цитата в разделе тега»; ключ `record_key = sha1(тег \| quote_id)`, `quote_id = sha1(текст \| автор)` |

**Как набран объём.** На сайте 100 цитат на 10 страницах ленты — меньше требуемых 200. По правилу задания
объём набирается разделами: после входа обходятся лента и разделы **всех** тегов, найденных в ленте.
Запись — факт «цитата опубликована в разделе тега». Дубли исключены ключом: та же цитата в том же теге
(повторный обход, перекрытие страниц, повтор после сбоя) даёт тот же `record_key`. Чтобы объём не выглядел
больше реального, отдельно указываются уникальные цитаты и теги:
записей **232**, уникальных цитат в парах 97 из 100 (цитаты без тегов в разделы тегов
не попадают — их 3), авторов 49, тегов 137, циклов (страниц) 152: 10 страниц ленты и 142 страницы разделов тегов.
Полнота проверяется сверкой: число пар по метатегам `keywords` ленты должно совпасть с числом пар, найденных
на страницах тегов (`compare.py → consistency_*`). В прогоне: 232 пары по ленте = 232 пары на страницах тегов,
не найдено 0, лишних 0 — у обоих подходов.

## 3. Схема реализации

```
                    ┌──────────── браузерный путь (collect.py, Playwright sync) ────────────┐
auth_state.json ──► │ context(storage_state) → «/» есть Logout? ── нет ──► /login: get_by_label  │
 (есть/нет)         │        │ да                         fill → Login → expect(Logout)       │
                    │        ▼                              → context.storage_state(path)      │
                    │ /page/1 → [wait_for_selector → eval_on_selector_all → клик Next          │
                    │   (expect_response + wait_for_url)] × N → теги из карточек               │
                    │ для каждого тега: /tag/t/page/1 → [... Next ...] → data_browser.csv      │
                    └──────────────────────────────────────────────────────────────────────────┘
                    ┌──────────── дешёвая альтернатива (light.py, requests.Session) ───────────┐
                    │ cookies из auth_state_light.json? → GET / есть Logout? ── нет ──►         │
                    │ GET /login → csrf_token (BeautifulSoup) → POST /login (form, та же cookie) │
                    │ → тот же общий Crawler: GET /page/N, GET /tag/t/page/N → data_light.csv    │
                    └──────────────────────────────────────────────────────────────────────────┘
                    compare.py: record_key браузера ↔ requests, поля по общим ключам
```

Общий для обоих путей цикл обхода (`common.Crawler`) гарантирует одинаковые предохранители, журнал и ключи;
различаются только «бэкенды» загрузки страницы. Извлечение одинаково по логике: JS-функция в браузере и
её копия на BeautifulSoup, нормализация (NFKC, пробелы, декоративные кавычки) — общая.

## 4. Локаторы и устойчивость к редизайну

| Назначение | Локатор (основной → фолбэк) | Тип | Оценка устойчивости |
|---|---|---|---|
| Поле логина | `get_by_label("Username")` → `input[name="username"]` | метка → атрибут-контракт | высокая |
| Поле пароля | `get_by_label("Password")` с проверкой `type=password` → `input[type="password"]` | метка → тип поля | высокая; фолбэк нужен, если метка ссылается на `for="username"` — в прогоне так и было: сработал `input[type="password"]` (browser.json → auth.password_locator) |
| Кнопка входа | `get_by_role("button", name="Login")` | роль + имя | средняя (зависит от языка) |
| CSRF | `input[name="csrf_token"]` | атрибут-контракт с сервером | высокая |
| Признак входа | `get_by_role("link", name="Logout")` | роль + имя | средняя (язык) |
| Карточка | `[itemtype*="schema.org/CreativeWork"]` → `div.quote` | микроразметка → класс | высокая |
| Текст / автор | `[itemprop="text"]` / `[itemprop="author"]` | микроразметка | высокая |
| Теги | `meta[itemprop="keywords"]@content` → `a.tag` | данные → класс | высокая |
| Goodreads | `a[href*="goodreads.com"]` → текст «Goodreads» | домен ссылки → текст | высокая |
| Next | `get_by_role("navigation").get_by_role("link", name=/^Next/)` → `li.next > a` | роль + имя → класс | средняя |

Структурного XPath и сгенерированных классов нет. Анализ трёх локаторов:

| Локатор | Переименование CSS-класса | Вставка обёртки `div` | Текст на другом языке | Что заменить |
|---|---|---|---|---|
| Next: роль `link` + имя `/^Next/` в `navigation` | не влияет (класс не используется); фолбэк `li.next > a` сломается | не влияет | **ломается**: «Далее» не совпадёт → фолбэк по классу | добавить `rel="next"` / `a[aria-label]` или брать ссылку с номером `page+1` из href (`a[href*="/page/N+1/"]`) |
| Карточка: `[itemtype*="schema.org/CreativeWork"]` | не влияет | не влияет (поиск не зависит от вложенности) | не влияет | устойчив; при отказе от микроразметки — `data-*` атрибут (`data-quote-id`) по договорённости с владельцем |
| Пароль: `get_by_label("Password")` + тип | не влияет | не влияет, пока метка связана с полем (`for`/вложенность) | **ломается** по метке («Пароль»), но спасает фолбэк `input[type="password"]` | сделать основным `input[type="password"]` внутри `form[action$="/login"]`: тип поля не зависит ни от языка, ни от вёрстки |

**Smoke-check** (`common.smoke_check`): после сбора проверяет наличие столбцов `text, author, author_url,
goodreads_url, tag` и печатает предупреждение, если доля пустых в любом превышает 5 %. Пустой `goodreads_url`
одновременно сигнализирует о потерянной сессии. Работоспособность показана в блокноте (§4): искусственное
обнуление 10 % `goodreads_url` вызывает предупреждение.

## 5. Сценарий взаимодействия и предохранители

Вход выполняется **один раз**: `ensure_auth` создаёт контекст из `auth_state.json` и проверяет «Logout»; только
если сессии нет — заполняет форму и сохраняет `storage_state`. Повторный запуск `collect.py --auth-check`
подтверждает вход без формы (журнал прогона: «[auth] сессия восстановлена из auth_state.json — повторный вход не нужен», режим
`reused_storage_state`, 1 запрос). Пагинация — клик
по «Next» с ожиданием ответа навигации (`expect_response`) и URL (`wait_for_url`), затем `wait_for_selector`
карточек; данные — одним `eval_on_selector_all`.

| Предохранитель | Значение | Где |
|---|---|---|
| Максимум итераций | 600 на запуск, 30 страниц на раздел | `Limits.max_iterations`, `max_pages_per_section` |
| Нет прироста N раз подряд | 2 страницы без новых ключей → раздел завершается | `Limits.stall_limit` |
| Лимит записей | 5000 | `Limits.max_records` |
| Лимит сбоев / времени | 10 сбоев (код 5) / 1800 с | `max_failures`, `max_runtime_s` |
| Потеря сессии | 1 повторный вход, затем `AuthLost` (код 2) | `Limits.max_reauth` |
| Сбой страницы | `TimeoutError` / HTTP ≥ 400 → png+html в `artifacts/`, 1 повтор, раздел пропускается, обход продолжается | `BrowserBackend`, `Crawler._fetch` |

Журнал `collection_log.csv` (по строке на итерацию): подход, этап, раздел, номер итерации и страницы, URL,
число элементов, прирост, накоплено, длительность, запросы, байты, статус, отметка времени.
Итог прогона: у каждого подхода 152 цикла (лента 10, разделы тегов 142), все со статусом ok; сбоев 0, повторных
входов 0; все 138 разделов (лента и 137 тегов) завершились штатно по причине `no_next` (ссылки Next нет), ни
один лимит-предохранитель не сработал. Среднее время цикла: браузер 0,62 с (лента) и 0,52 с (теги), requests —
0,34 и 0,27 с (`metrics/summary.md` §3).

Методика: время — `perf_counter` от запуска до сохранения (включая паузы вежливости 1 с; их сумма — в

**Оговорка о трафике.** Строка «Трафик» сравнивает разные величины. По журналу `collection_log.csv` первая
страница ленты у браузера весит 2 263 байт (тело в gzip), у requests — 12 135 байт, т. е. распакованный HTML
(11 928 байт) плюс заголовки: счётчик `raw.tell()` в этом прогоне учёл тело без сжатия. Поскольку браузер с
блокировкой ресурсов загружает те же 155 HTML-документов, что и requests, при одинаковом сжатии трафик
подходов практически равен; разница в 4 раза — следствие методики, а не подхода. Сравнимы число запросов (155 = 155),
время и память. **Главный итог:** без учёта одинаковых пауз вежливости requests быстрее в 1,9 раза
(41,47 против 80,07 с) и требует в 14,4 раза меньше памяти (49,8 против 715,9 МБ).

## 8. No-code реализация (n8n)

Workflow `nocode/workflow.json` (импорт и запуск — `nocode/INSTRUCTIONS.md`): Manual/Schedule Trigger →
Config → `GET /login` (полный ответ с заголовками) → HTML Extract `input[name="csrf_token"]@value` →
`POST /login` (form-urlencoded, cookie из `Set-Cookie`, без следования редиректу) → If «ответ 3xx» →
Code «склеить cookie» → цикл по ленте (Code «Шаг ленты» → HTTP Request одной страницы → Code «Следующая
страница?» → If → Wait 1 с → снова «Шаг ленты»; не больше 15 страниц) → Code «Страницы ленты» → HTML Extract
карточек → Split Out → HTML Extract полей → Code нормализации → Remove Duplicates → Code smoke-check →
Convert to File (CSV) → Write File (`~/.n8n-files/lab4/nocode_result.csv`, копия — `nocode/nocode_result.csv`).
У трёх HTTP-узлов Retry On Fail (5 × 5000 мс) и ветка ошибки → Set «детали сбоя» → Stop and Error.

**Что выяснилось при реальном запуске (16.10.2026).** На Mac автора часть новых TLS-соединений обрывается: замер `curl` — 4 из 10 рукопожатий с `quotes.toscrape.com` завершились ошибкой `rc=35` (в другие минуты 0–2 из 6–8). Python-сборщики этого почти не замечали: `requests.Session` и браузер держат одно соединение (keep-alive), а редкие обрывы закрывают повторы. n8n открывает новое соединение на каждый запрос, а Retry On Fail повторяет узел, только если ошибкой стал **первый** item выхода (n8n-core 2.35.5, `workflow-execute.js`: `checkFailure` проверяет `data[0][0].json.error`). Встроенная пагинация HTTP Request выполняет все страницы внутри одного запуска узла: обрыв на любой странице валит узел, а повтор начинает ленту заново. Первые 4 запуска исходной версии закончились ошибкой «Client network socket disconnected before secure TLS connection was established» (видны в `screenshot_execution.png`). Поэтому пагинация переделана в цикл: «Шаг ленты» → «GET /page/N (страница ленты)» — один запрос за запуск узла, Retry On Fail 5 × 5000 мс (максимум n8n) → «Следующая страница?» (ссылка Next, предохранитель 15 страниц) → IF → «Пауза 1 с (лента)» → снова «Шаг ленты»; после последней страницы «Страницы ленты» разворачивает накопленный HTML в items. После переделки — 5 успешных запусков из 5, в трёх из них сработали повторы отдельных страниц (1–2 на прогон).

До сдачи workflow проверен импортом и запуском в n8n 2.43.6 на локальной имитации сайта (не на реальном):
ветка входа, пагинация, запись CSV и ветка ошибки отработали. При проверке найдена ловушка: узел HTML (v1.2)
получает текст через html-to-text с переносом строк по 80 символов, а опция *Clean Up Text* удаляет переносы без
пробела и склеивает слова — поэтому в узлах HTML она выключена, пробелы нормализует узел «Нормализация».

Рендеринг-API не используется: по диагностике страницы серверные, поэтому **запросов с JS-рендерингом —
0** за прогон; один прогон = 2 + P обычных запросов (P — страниц ленты). Если бы рендеринг требовался, каждая
страница стала бы платным запросом к рендеринг-API: для 10 000 записей в день ≈ 1 000 рендер-запросов в день.
Ограничения: в n8n нет общей cookie-сессии (cookie передаётся заголовком вручную), ссылка «Next» ищется
регулярным выражением, браузера нет. Результаты прогона (n8n 2.35.7, 16.10.2026): строк 100, время сборки ⟪ЗАПОЛНИТЬ⟫ мин,
время прогона — медиана 25,9 с (21,7–37,9 с по 5 запускам), запросов 12 + 0–2 повтора, совпадение с лентой
браузера — 100 из 100 цитат по паре (текст, автор), расхождений `goodreads_url`, `author_url` и тегов — 0;
скриншоты — `nocode/screenshot_*.png`.

## 9. Задания повышенной сложности

**Параллельный сбор** (`parallel.py`): `async_playwright`, один браузер, K = 3 контекста из одного
`storage_state`, очередь тегов, по одному воркеру на контекст (это и есть ограничение одновременности),
пауза вежливости у каждого воркера. Тот же код запускается с K = 1 на тех же 30 тегах. Результат:
K=1 41,0 с, K=3 19,37 с, ускорение ×2,12, ошибок 0, наборы совпадают (47 записей)
(и с `data_browser.csv` — тоже совпадают). Ускорение меньше ×3: у тегов разное число страниц, и в конце очереди
работает один воркер; кроме того, у каждого воркера своя пауза 1 с, т. е. нагрузка на сайт при K=3 — до 3 запросов
в секунду. Для учебного сайта это допустимо, для реального — только по согласованию с владельцем.

**Подмена ответа** (`faults.py`, `route.fulfill`; API в пайплайне нет, поэтому подменяются ответы на
навигацию): (1) `/page/3/` — 200 без карточек: ожидание карточек завершается `TimeoutError`, сохраняются
png+html, 1 повтор, лента останавливается со статусом ошибки, страницы 1–2 сохранены; (2) первый тег — HTTP 500:
ошибка `http_500`, артефакты, повтор, тег пропускается, следующие теги собираются; (3) страница тега «как
у анонима» (без Logout): ровно один повторный вход, затем `AuthLost` вместо бесконечного цикла входов.
Итог (`metrics/faults.json`): все три проверки **PASS**. (1) empty — 2 сбоя (попытка и повтор), лента остановлена
с `error:timeout`, 20 цитат со страниц 1–2 сохранены, png+html для обеих попыток в `artifacts/`; (2) http500 —
тег `abilities` остановлен с `error:http_500` после повтора, следующие теги `activism` и `adulthood` собраны
(`no_next`); (3) expired — ровно 1 повторный вход, затем `AuthLost: повторный вход не восстановил сессию`.

**Trace Viewer.** `artifacts/trace.zip` — вход и лента основного прогона; `artifacts/trace_faults.zip` — инцидент
HTTP 500. Разбор (`python -m playwright show-trace artifacts/trace_faults.zip`):
1. `Page.goto /page/1/` → документ 200, в снимке DOM видны карточки и «Logout» (сессия из `storage_state`);
2. `wait_for_selector` карточек выполнен сразу, `eval_on_selector_all` вернул 10 записей;
3. `Page.goto /tag/<тег>/page/1/` → во вкладке Network ответ **500** с телом `Internal Server Error`
   (помечен как обработанный `route.fulfill`);
4. сборщик не ждёт карточки на странице ошибки: статус ≥ 400 → `page.screenshot` и `page.content` (видны как
   отдельные действия в трассе) → исключение `PageError(http_500)`; браузер и контекст закрываются в `finally`.
Длительность шагов (по событиям `trace.trace`; сценарий целиком ≈ 2,75 с): `newPage` 29 мс;
`goto /page/1/` 2 639 мс — почти всё время, это ответ реального сервера (в трассе видны `Route.continue` для
документа и два `Route.abort` для CSS — работает блокировка ресурсов); `waitForSelector` 14 мс;
`evalOnSelectorAll` 3 мс; поиск Next и проверка Logout — 2–4 мс; `goto /tag/abilities/page/1/` 6,7 мс (из них
`Route.fulfill` 0,9 мс: ответ 500 сформирован локально, запроса к серверу не было); `page.screenshot` 25 мс;
`page.content` 0,5 мс. В трассе одна попытка: это отдельный короткий сценарий `_trace_incident` без цикла
повторов; повтор и пропуск тега проверены сценарием http500 выше. Вывод: трасса однозначно показывает, что сбой — ответ сервера, а
не ошибка локатора или таймаут, и что ресурсы освобождены.

## 11. Правовая и этическая оценка

- **Площадка.** `quotes.toscrape.com` — учебный сайт Zyte, созданный для тренировки парсинга; коммерческие сайты
  не использовались. Вход — учебный механизм сайта (принимаются любые логин и пароль), реальные аккаунты не
  задействованы; автоматизация входа в реальные сервисы в работе не выполнялась.
- **robots.txt и нагрузка.** `robots.txt` проверяется перед каждой страницей (`RobotsGuard`, ROBOTSTXT_OBEY);
  на сайте его нет (HTTP 404), т. е. ограничений нет. Пауза 1 с между запросами, у параллельного режима —
  у каждого из 3 воркеров; честный User-Agent `PSU-edu-crawler/1.0 (+ссылка на репозиторий; student lab)`; таймауты
  и ограниченные повторы.
- **Защита не обходится.** CSRF-токен не подделывается и не подбирается: он берётся из формы и отправляется так
  же, как это делает браузер пользователя; капчи и антибот-защиты на площадке нет, средства их обхода не
  применялись. Эндпоинт `/api/quotes` проверен только в диагностике и для обхода входа не использовался.
- **Персональные данные (152-ФЗ).** В наборе — имена авторов цитат (известные публичные персоны), ссылки на их
  публичные страницы и тексты цитат; данных частных лиц нет. Имя автора формально относится к персональным данным;
  обработка ведётся в учебных целях, без распространения и обогащения, набор не публикуется вне курса
  (ст. 6 и ст. 10.1 152-ФЗ о распространении данных, разрешённых субъектом). Учебные креды и cookie сессии
  (`auth_state*.json`) не являются данными реального человека.
- **Авторское право.** Короткие цитаты с указанием автора и источника используются в учебных целях
  (ст. 1274 ГК РФ — свободное цитирование в научных и учебных целях).
